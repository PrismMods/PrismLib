# Facet — a UI Toolkit engine for Unity mods — design

Date: 2026-11-06. Status: written from the conversation, reviewed by a builder check, and the user's answers are folded in. Waiting for the user's corrections. "Facet" is a working name.

The user handed the engine's internals to the writer: "decide and explain in the spec, I'll correct anything that seems wrong". So every decision below is the writer's call unless it is marked **(user)**. Calls with a real alternative say what the alternative was.

## What it is

Facet is a UI engine for Unity mods, built on UI Toolkit. It plays the role O5Kit plays for Overlayer v5: one shared kit of windows, controls, theming, navigation and search, so that a mod's settings screens are a page of data and calls instead of a framework of its own.

It lives in **its own repository and ships as a standalone mod (user)**, so that people outside PrismMods can use it. It targets **any Unity game on Mono, and later IL2CPP (user)**. A friendly, documented API for outside modders is wanted **eventually, but not now (user)**. v1 is about a robust core.

## Why

- **Quartz is moving to UI Toolkit (user).** Its ~12k lines of uGUI came from Overlayer by way of KorenResourcePack. They have no data binding: profile switches, resets and addon reloads all go through a full `UICore.Rebuild()`. An import does not even do that, so it probably leaves stale controls on screen.
- **PrismLib.UI already proves runtime UI Toolkit works.** It works in ADOFAI 3.x (Unity 6), and every landmine in `PrismLib/CLAUDE.md` § UI was paid for in-game: fonts that don't inherit, a missing theme style sheet, no clipping, flex shrink, wheel delivery, fonts by file. That knowledge is general-purpose. Today it is locked inside a library that is tied to ADOFAI and shipped "first copy loaded wins".
- **Nothing like O5Kit exists on UI Toolkit.** O5Kit itself is uGUI and LGPL, and Overlayer is GPL. So this design takes **ideas** from them and copies no code.
- **Licence of the starting code (user).**
  - Quartz is GPL-3.0 only because of the Overlayer code in it.
  - The parts PrismLib.UI took from Quartz (the search matcher and the accent derivation) and from Topaz (`Nav`, `SearchIndex`, `ColourPicker`, `GradientEditor`) are the team's own work, not based on GPL code.
  - So Facet can start from them under MIT.
  - This matches the code: Overlayer has no search matcher and no accent derivation.

## Milestones (user, in this order)

1. **The engine.** A new repository, the core described below, a gallery mod and both test suites.
2. **Prism · Settings on Facet.** PrismLib.UI's settings window is the first real screen. Topaz, Sapphire and CamDisplay keep building and keep working at every step.
3. **One page of Quartz's menu on Facet**, next to its uGUI menu. **Planned, not confirmed (user).** This project writes its plan and builds it only once the user confirms it.

## Goals

- A game-agnostic and loader-agnostic engine. It covers surfaces, windows and layers, theme, a set of controls bound to live values, a nav shell, search, fonts, input routing, undo and error isolation.
- Live re-theme and live re-language. Both re-apply to a window that is already open, with no rebuild.
- In-place refresh. A value changed behind the UI shows up in the control where it sits.
- Several mods, and several Facet versions, in one process without stepping on each other.
- Prism · Settings, then a Quartz page, running on it. No visible regression, and within the existing performance budget.

## Non-goals (v1)

- **An IL2CPP build.** The API is designed so IL2CPP stays possible (see "IL2CPP rules"); building and verifying it on a real IL2CPP game is later work.
- **Polish for outside modders**: documentation site, samples, and a stable 1.0 API. Versions stay 0.x until then.
- **A BepInEx entry point.** v1 ships MelonLoader and UMM entries, because ADOFAI uses those.
- **Quartz screens beyond one page**, and the widgets only those screens need: card grid, drag-to-reorder list, the KeyViewer canvas editor, the TUF browser, resizable split panes.
- **Settings UI generated by reflection over attributes**, as Quartz's addon `RegisterSettingsTab` does. It comes with Quartz's addon API, later.
- **USS or UXML.** They cannot be authored at runtime; everything stays inline C#.
- **Moving the update toast.** It stays uGUI by the `ToastStack` convention (`PrismLib/CLAUDE.md`).

## Anti-goals

- **Breaking a released mod.** PrismLib.UI keeps every public type and signature. Each mod builds at every commit of milestone 2.
- **Losing performance.**
  - The first Prism window must still open within the 50 ms `[perf]` budget, after warm-up.
  - A hidden window must do no per-frame work.
  - Nothing may log per frame. The font flood of ~10,000 lines a second is the cautionary tale.
- **One mod's exception taking down a window**, or another mod's UI. Every call into consumer code is guarded.
- **Game knowledge in Facet.** The engine must not refer to RDInput, scenes, `Assembly-CSharp`, UMM or Harmony. ADOFAI-specific parts stay in PrismLib.
- **Copying GPL or LGPL code** from Overlayer, O5Kit, or the Overlayer-derived parts of Quartz into Facet.
- **A rewrite for its own sake.** Facet starts as a copy of PrismLib.UI's general-purpose Toolkit files, which are MIT and by the same authors. It changes only where this design says so, and keeps the reasons recorded in their comments.

## Constraints

- **Unity 6 is the only verified version.** ADOFAI 2.9.x builds do not run Unity 2022, so Prism's UI Toolkit mods support ADOFAI 3.x only (user). That was expected and is part of the plan, and there is no Unity 2022 game to test on.
- **Compile against Unity 2022.3 reference assemblies anyway** (my call). That keeps Facet loadable in the many mod-able games on 2022 without binding a Unity-6-only API. Unity 2022 support is "compiled for, unverified" until someone tests a 2022 game.
  - Unity-6-only features, such as the SDF `CreateFontAsset` overload and the text field placeholder, stay behind reflection, as they are today.
  - The pre-6 workarounds (`HandDownFonts`, the macOS font files tried first) stay as they are, also unverified.
  - The alternative was compiling against Unity 6 and dropping all of that. It is cheaper today, but every 2021/2022 game would be locked out.
  - BepInEx's NuGet feed (`nuget.bepinex.dev`) publishes per-version reference assemblies as `UnityEngine.Modules`. Version `2022.3.0` exists; checked 2026-11-06. Use the lowest 2022.3 patch, since anything present there is present in every later 2022.3 release.
- **`netstandard2.0`** (my call). PrismLib.UI builds with xbuild for .NET Framework 4.8, which cannot reference a `netstandard2.1` assembly. 2.0 is consumable by PrismLib.UI, Quartz (`netstandard2.1`) and any Unity 2018+ mod.
- Facet ships no Harmony, no game DLL reference and no loader reference, except in the standalone mod's tiny entry assemblies.
- The UI Toolkit landmines listed in `PrismLib/CLAUDE.md` § UI apply unchanged. Facet's code keeps the comments that record them.

## Packaging and coexistence

**One shipped DLL, `Facet.<major>.<minor>.dll`** (idea from O5Kit).
- The namespace is always `Facet`.
- Mods built against the same minor share one loaded copy.
- Different minors load side by side, each mod getting the one it was built for.
- A patch release keeps the name and is a drop-in replacement.
- Within one minor, changes are append-only: new enum members go last, new members on classes are fine, existing signatures never change. That is today's PrismLib.UI rule, scoped to a minor.
- This ends the NoInlining-and-catch dance for engine APIs: a mod always gets the Facet it was compiled against, as long as it ships it.

**The alternative was keeping PrismLib.UI's model**: one name, first copy loaded wins, bridges for every newer API. It was rejected because outside modders would have to learn the bridge rules before they could use the engine.

**Cross-version coordination.** A few things must agree across every loaded Facet, or two versions fight:
- **Window stacking:** the `sortingOrder` bands.
- **Escape:** answered once per frame, by the topmost window of any version.
- **Host-facing questions:** "is any window open", "is the pointer over one", "is a text field focused", "does any window block game input".
- **Key capture:** which control currently owns the capture.

These live in one dictionary of plain BCL values and delegates, stored with `AppDomain.CurrentDomain.SetData("Facet.Shared", …)`, so that every version can read it. Each version registers delegates there, and the public queries union them. Keep it to the list above.

**Distribution, each optional:**
- A mod ships `Facet.x.y.dll` beside its own DLL, as PrismLib.UI is shipped today.
- A player installs the **standalone mod** once:
  - MelonLoader: `UserLibs/Facet.x.y.dll` plus `Mods/Facet.dll`.
  - UMM: a `Facet/` folder with `Info.json`.
  - The entry assemblies do two things: put Facet where resolvers find it, and add the **Gallery**. The Gallery is a window with every control, a theme and accent switcher and a language switch, opened by a hotkey the host configures. It is also where the in-game autotest runs.

**Repository** `PrismMods/Facet`, MIT (my call; it matches PrismLib and keeps Facet usable from both GPL and closed mods). Created locally first; the GitHub repo is made when the user says so.

## Architecture

### Host: one per consumer

`Facet.Host` is the context a consumer creates once, e.g. `Host.Create("Topaz", o => { … })`. It holds:
- the consumer's name;
- its log sink;
- its translator and language;
- its persistence: `Read(key)` and `Write(key, value)` for window geometry and fold state;
- its default theme and font overrides.

Every surface belongs to a host.

**This replaces today's global statics that one mod overwrites for all:** `Ui.Log`, `Words.Language`, `Window.Read`/`Write`, and pushing colours into `Tokens`. For example, `Ui.Log` currently points at whichever mod assigned it last. O5Kit's `O5Context` is the same idea, and O5Kit still has shared statics; Facet's only shared static state is the cross-version dictionary above.

**Finding an element's host.** An element finds its host the way `Theme.For` finds a theme today: the nearest ancestor that was given one, else the host whose build is in progress. A window that shows several mods' rows gives each row's subtree that row's host. Prism · Settings does exactly this.

### Surfaces, windows and layers

These carry over from PrismLib.UI as they are:
- `Layer` (Hud, Window, Popup, Modal, Tooltip) with its `sortingOrder` bands;
- `display` instead of `SetActive`;
- `BringToFront`;
- Escape routing (a focused field blurs first, then the surface's handler runs, then it hides);
- the `Hidden` event;
- `Window`: drag, resize, scale, clamp, persisted geometry, title bar, search box, footer, undo/redo buttons.

Changes:
- **The close button raises `CloseRequested`**, and the default handler hides the window (from O5Kit). An owner can animate or veto.
- **The panel model is unchanged: one `PanelSettings` and `UIDocument` per surface.** The alternative is one panel per layer, with windows as children ordered by element order. That would be cheaper to open and would need no `sortingOrder` counters. It was left for later because today's model is verified in-game and inside budget. Measure it with `[perf]` before changing it.
- **Warm-up is generic.** The first surface schedules a throwaway off-screen window containing one of every control, as `SettingsPanel.WarmUp` does today. PrismLib.UI then needs no warm-up of its own.

### Styling: roles, looks and live re-theme

**Colours are roles, never values.** A widget never writes a `Color`. It says which role an element's background, text or border uses: `Paint.Bg(e, Role.Panel)`. Facet remembers that per element and applies the current theme's value.

**A theme change walks each surface that wears it and re-applies the roles.** That is the live re-theme Quartz fakes today: it caches every `Image` and `TMP_Text`, then remaps any colour within 0.018 of an old palette slot. O5Kit has no live re-theme at all.

**Roles.** Today's ten stay: Panel, PanelBorder, TitleBar, Row, RowAlt, RowHover, Text, TextMuted, Accent, Danger. Added:
- **AccentText**: text on an accent background. Today it is a hard-coded near-black in `Ui.Highlight`.
- **Focus**: the keyboard focus ring.

Roles are appended only, so a new role never breaks a mod built earlier.

**Theme derivation.** `Theme.FromAccent(accent, tint)` keeps Quartz's derivation, already ported in `Theme.Recolour`. The `with`-style derivation and presets O5Kit has are not needed in v1: an accent plus a tint is how every Prism mod themes.

**Looks.** A look is a per-state recipe of roles: resting, hover, pressed, selected, disabled and focused, for background, text and border. Facet tracks those states itself and registers its pointer and focus callbacks once per element. `Facet.Select(e, bool)` and `Facet.Enable(e, bool)` drive the states that are not pointer-driven.

Looks replace hand-written code scattered across today's code:
- `Ui.BtnColors`, `Ui.Highlight` and `Ui.Flat`;
- every `MouseEnterEvent`/`MouseLeaveEvent` colour lambda in Widgets, Nav and Window;
- `Window.Enable`'s opacity fade.

A runtime panel has no theme style sheet, so `:hover` and `:disabled` do nothing. That is why each widget grew its own copy of this code.

Named looks in v1: Button, FlatButton, AccentButton, DangerButton, Row, RailItem, Field, Card, Chrome. More are added as screens need them.

**Sizes stay global in `Tokens`.** They are not per theme: no mod changes them at runtime, and Window scale covers "bigger".

**Animation.** `Anim` keeps its helpers and gains a global speed multiplier (from O5Kit). Zero means instant. The autotest uses zero, and a reduced-motion setting can use it later.

### Text, languages and fonts

**Every string is stored as its English key.** Each text element Facet builds keeps that key and translates it through its host.
- On a language change, each surface re-translates its text in place, with no rebuild (from Quartz's `TextLocalization.RefreshAll`).
- **A host's table answers only its own strings.** That is today's `Words` ownership rule, without the assembly-name guess: the host is known from the element.
- Facet's own words come from Facet's own table, which is today's `Words.Own`.

**Fonts carry over unchanged:**
- order: files first, then OS families, then a font the consumer supplies;
- three slots: regular, bold as a real weight-700 face, and mono;
- 64 px sampling with 6 px padding, and the glyph preload;
- `HandDownFonts` on Unity before 6000;
- one shared `PanelTextSettings` with an empty fallback list.

The candidate file lists become host-overridable, so another game or OS can add paths. The builder confirms Korean text still renders on macOS in ADOFAI 3.x; that is today's behaviour and must not regress.

### Controls and binding

**A control is bound to a value.** It takes a `Bind<T>`:
- `Bind.To(() => S.X, v => S.X = v)` for a live value;
- `Bind.Value(initial, onChange)` for today's snapshot style.

**Each control returns a handle**, `Control<T>`. The handle is a plain class, not a `VisualElement` subclass (see "IL2CPP rules"). It has:
- `Root`: the row element;
- `Value`;
- `Set(v, notify = true)`;
- `Refresh()`;
- `OnChanged` (every change) and `OnCommitted` (end of a drag or edit). That split is from O5Kit.

**Options go in an options object with a configure lambda**, e.g. `Controls.Slider(parent, "Size", bind, o => { o.Min = 0; o.Max = 2; o.Default = 1; })` (from O5Kit).
- An unset option means the theme's or the control's default.
- New options are new settable properties, which is binary-safe within a minor. New optional parameters would not be.

**Common options:**
- `Tooltip`, or `TooltipText` (a `Func<string>` evaluated on hover);
- `Default`: shows a "changed" dot when the value differs from it, and a middle-click on the row resets the value to it (from both O5Kit and Quartz);
- `EnabledWhen` and `VisibleWhen` predicates;
- `ContextMenu` items for a right-click. This is how Quartz will hang "bind a hotkey to this toggle" on its rows.

**Refresh in place.**
- While its surface is visible, Facet re-reads every bound control on a fixed interval. The default is 100 ms, and the host can change it.
- When the read differs from what is shown, the control updates its display without notifying.
- **A control the user is editing is skipped**: a focused field, or a slider being dragged.
- Undo, redo and `surface.Refresh()` re-read at once.
- Hidden surfaces read nothing.

This replaces three mechanisms:
- PrismLib's `History.AfterApply` causing a whole-page `Nav.Refresh()` rebuild;
- Quartz's full `Rebuild()`;
- O5Kit's per-field `O5Watcher`.

Polling was chosen over change notification because the values belong to the mods' own settings classes, which notify nobody. A poll needs no cooperation from them and covers profile switches, imports and outside writes alike.

**Undo.** Every set goes through `History`, keyed per control: host, page and label, plus an id. The key is never the label alone, for the reason the layout editor recorded: a label key undoes into whatever is selected later. `History` keeps its coalescing and its `Applying` guard.

**v1 control set.** Today's set carries over:
- Toggle, Slider, IntSlider, Choice (segmented), Text, Info;
- Action, Danger and DangerButton (armed, click twice);
- Colour (ColourPicker), Key;
- Section (fold state now persisted through the host), Header, Spacer;
- ToggleGroup, SubPage, ToggleSubPage, Item, MarkActive.

Added, because Quartz's pages need them:
- **Dropdown**: a button that opens `Popup.Menu`, for long option lists. It takes an optional per-item font, which Quartz's font picker uses.
- **Number**: a typed number field without a slider.
- **Slider options**: `Step` (snap) and `Scale` (linear or log, from O5Kit's `IValueScale`). These are options, not new controls.

`GradientEditor` comes along as it is.

### Pages, navigation and search

**Nav carries over:** rail, groups, branches, pushed subpages, the collapsible rail and the breadcrumb element. It gains:
- **an owner on each `NavItem`**, with `Nav.RemoveOwner(owner)`, so a mod or addon that unloads takes its pages with it (from Quartz's `NavRegistry`);
- a `VisibleWhen` predicate on items;
- remembering the last page opened inside each branch;
- **keeping the scroll position** when a page is rebuilt.

**Pages are built lazily, on their first visit, and are not rebuilt for value changes**: binding covers those. A page rebuilds only when its `Revision` changes or the owner calls `Rebuild()`.

**The search index is built lazily, on the first query.** Today `Nav`'s constructor builds every page into a throwaway container to index it, which is part of what a first open pays for. Quartz's first search makes the same mistake, through `EnsureAllBuilt`.
- The index is cached per language until the pages change.
- A `[perf]` line records how long it took to build.
- Rows contribute their metadata while they build: label, English key, tooltip, section and page.

**The matcher is plain BCL code and tested offline.** It ports Quartz's `SearchMatcher` and `SettingsSearch` behaviour:
- every query token must land in the label, section, page or tooltip, in English or in the player's language;
- Korean initial-consonant (초성) matching;
- a fuzzy edit-distance pass only when the exact pass finds nothing;
- ranked results.

It starts from PrismLib.dll's `Search`, which is the team's port of Quartz's matcher (see "Licence of the starting code"), and adds the 초성 and fuzzy passes.

Once Facet's matcher is in use, PrismLib.dll's `Search` is frozen and marked obsolete, and bridges stop passing it in as `SearchIndex.Scorer` and `SettingsPanel.Matcher` (my call). It is not deleted, because it is public API. One matcher, not two that drift apart.

**A hit:**
1. opens the page;
2. unfolds every folded section that contains the row;
3. scrolls each scroll view on the way so the row is in view;
4. flashes the row.

**Forms.** A `Field` descriptor describes one setting: owner, page, group, label, tooltip, kind, bind, range, step, options and default. `Form.Build(parent, fields)` builds controls from a list of them. This is today's `SettingRow` schema, made Facet's own. PrismLib's bridge converts `SettingRow` to `Field`.

### Input

These carry over from `Ui`:
- **Escape** routing, once per frame across hosts and versions; a host that spent the key calls `ConsumeEscape`;
- `PointerOverWindow`;
- the polled wheel fallback, `TickWheel`, because `WheelEvent` delivery differs between panels;
- drawn cursors.

New:
- **`TextFocused` comes from `FocusIn` and `FocusOut` events** (a count), instead of walking the focus controller on every query. Hosts check it before acting on their hotkeys (O5Kit's `O5InputBlocker` idea, event-driven).
- **One key-capture owner at a time** (Quartz's `KeyCaptureCoordinator`). A new capture cancels the old one with a callback. The keys themselves are read by the host, because reading keys is game-specific: Prism uses `MacKeys` there.
- **`Facet.WantsInput`**: true when any visible blocking surface, the pointer over a window, or a focused text field says so. Blocking the game's own input stays the host's job. For ADOFAI, PrismLib's `InputGate` reads this.

**Keyboard focus.** Controls are focusable and draw a focus ring through the Focus look state. Tab order is the build order. Arrow-key navigation inside rails and menus is left for later.

### Error isolation

**One guard, `Safe.Run(host, site, fn)`, wraps every call into consumer code:**
- page builds, gets, sets and clicks;
- tooltip functions, `Revision`, and the `VisibleWhen`/`EnabledWhen` predicates;
- translators, escape handlers and `CloseRequested` handlers.

**Logging:**
- Each message names the host and the site, with the first stack line.
- **One message per host and site per 10 seconds**, so a getter that throws on every refresh cannot flood the log.

**What the user sees:**
- A page that throws while building shows an error card instead: "This page failed to build — see the log", with the owner's name.
- A row that throws while building shows as an unavailable row.
- A getter that throws three times in a row puts its control in an unavailable state and stops polling it until the page rebuilds.

Facet's own per-surface work, such as refresh and re-theme, is guarded per surface too. A Facet bug in one window does not stop other windows.

O5Kit has none of this, and Quartz guards page builds but not control callbacks. PrismLib.UI guards most of it today, so Facet makes it uniform.

### IL2CPP rules, kept from day one

1. **No public type derives from a Unity type.** Handles are plain classes. Today's factories already return plain elements.
2. **Every `RegisterCallback<T>` goes through one helper**, `Facet.Events.On<T>`, so an IL2CPP build has one place to convert delegates.
3. **Per-element engine data goes through one store**, `Facet.Data`, instead of reaching for a `ConditionalWeakTable` keyed by element. On Mono it is a `ConditionalWeakTable`.
   - Under Il2CppInterop a wrapper object may not keep its identity across calls; that is unverified. An IL2CPP build can then key the store by the native pointer.
4. **No API depends on a Unity type that games commonly strip.**

**Whether an IL2CPP game even contains `UIElementsModule` is the first thing to check** when IL2CPP work starts. A game that never used UI Toolkit may have been stripped of it.

## Performance budgets

Recorded as `[perf]` lines by the Gallery autotest, and by LayoutProbe for Prism's windows:

| What | Budget |
|---|---|
| First window opened after warm-up | ≤ 50 ms (today's check) |
| A hidden window | no per-frame work |
| One refresh pass, 100 bound controls visible | ≤ 0.2 ms |
| Re-theming an open window | ≤ 16 ms |
| First search index (Topaz's menu, every page) | ≤ 100 ms; if over, build it a few pages per frame |

## Testing

**Offline.**
- Facet's `Core/` folder holds the BCL-only logic: the matcher and 초성 tables, theme derivation math, history coalescing, value scales and clamping, binding diff rules, and the cross-version dictionary rules.
- It is compiled straight into a console test with `Check()` lines ending in ALL PASS, like `PrismLib/tools/PrismLibTest.cs`.
- The test may reference `UnityEngine.CoreModule` for `Color` only, and calls no engine method in it. O5Kit's tests do the same.

**In-game.** The Gallery's autotest mode is triggered by an `autotest` file, like LayoutProbe's. It:
- drives synthetic UI Toolkit events against real panels: a click, a drag, typing, Escape, the wheel, a middle-click reset;
- re-themes and switches language while a window is open;
- makes a getter throw on purpose;
- writes PASS/FAIL and `[perf]` lines, then quits the game.

**Prism's existing suites stay the acceptance test for milestone 2:** PrismLib's offline test, LayoutProbe's autotest and its `[perf]` budget, and CamDisplay's self-test. One in-game test runs at a time. The test-rig rules are in `PrismLib/CLAUDE.md` and in memory.

## Milestone 2 in more detail: PrismLib.UI on Facet

PrismLib.UI keeps every public type and every signature. Its general-purpose files become thin layers that call Facet, through one default host per mod set up by the bridge. Its ADOFAI-specific files stay where they are and build on Facet's primitives:
- `InputGate`, `MacKeys`, `FontFix`;
- `DebugPanel`, `LayoutEditor*`, `EditTarget`, `LayoutMath`;
- `FpsCounter`, `RestartPrompt`.

**Order, each step building every mod and passing every suite:**
1. Facet ships beside PrismLib.UI, unused:
   - each mod's `release.sh` and `dev.sh` copy `Facet.x.y.dll` too;
   - the resolver finds it;
   - `tools/check-bridge.sh` loads with it present.
2. `Surface`, `Window`, `Theme`, `Tokens` and `Words` delegate to Facet. Every Prism window now stands on Facet surfaces.
3. `SettingsPanel` schema mode runs on Facet's `Form` and `Nav`. **This is Prism · Settings, the first screen.**
4. `Widgets` delegates to Facet's controls, which moves Topaz's menu (`SettingsPanel` nav mode) onto Facet.
5. `History.AfterApply` stops forcing a page rebuild, now that binding refreshes in place.

Where a PrismLib.UI signature takes a value and a callback, the layer wraps it in `Bind.Value`. Live binding comes when a mod moves a page to Facet's own controls.

## Milestone 3 in more detail: a Quartz page

**The bridge.** Quartz references Facet directly. It ships beside Quartz, so it needs no PrismLib-style bridge.

**The page.** It lives in a Facet window, opened from Quartz's existing menu and coexisting with it. Both edit the same config object, as Topaz's two menus did.

**Which page.** EffectRemover (32 toggles) or KeyViewer Tuning (33 sliders): a page that stresses rows and binding.

**The window's theme** comes from Quartz's accent. Dragging Quartz's accent picker re-themes the Facet window live.

**This milestone is planned, not built**, until the user confirms it. Its plan has to cover:
- referencing Facet through Quartz's generated stubs and its `gen-stubs.sh --check` release gate;
- packaging Facet into Quartz's dist and its update engine;
- hooking Quartz's accent picker;
- Quartz's uGUI canvas drawing above UI Toolkit panels.

## Calls the writer made (check these)

1. The name "Facet", the repository `PrismMods/Facet`, and the MIT license.
2. Versioned DLL names plus a cross-version dictionary, instead of PrismLib.UI's "first copy loaded wins".
3. `netstandard2.0`, compiled against Unity 2022.3 reference assemblies though only Unity 6 is verified.
4. Hosts per consumer, replacing global statics.
5. Colour roles with looks and live re-theme, instead of colours copied in at build time.
6. Polling refresh at 100 ms for bound controls, instead of change events.
7. Lazy search indexing, and Quartz's matcher behaviour reimplemented.
8. One `PanelSettings` per surface kept for v1.
9. The standalone mod carries a Gallery that doubles as the in-game test.
10. IL2CPP is designed for but not built.
